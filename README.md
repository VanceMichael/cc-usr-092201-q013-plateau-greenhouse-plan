# 高原温室生产协同

保存高原温室以季次为单位的种植计划、农技方案、资源排程和采收批次。

## 资料范围

领域资料位于 `fixtures/domain.json`（当前 version 2），结构约定见 `contracts/domain.schema.json`。当前记录类型包括温室棚区、作物季次、土壤检测、农技方案、田间操作、采收批次，状态示例为待定植 → 生长中 → 需干预 → 待采收 → 已采收 → 已交付。这些样例使用虚构标识，不含真实个人资料、账号或连接凭据。

已整理的业务事实：

- 村庄海拔约1400米，新建近百座日光节能温室并配套高山区滴灌工程
- 外省技术员给出的水肥基线方案需要按逐棚土壤检测结果适配
- 技术团队会根据土壤差异调整有机肥和生物制剂
- 工人与滴灌设备数量有限，各类班次经常在同一计划窗口撞期
- 园区以作物季次为单位组织土壤检测、育苗、植保、水肥配方、班次与采收订单
- 园区同时组织种植、采摘和冷链运输

## v2 协同约定

- **季次排程**（`planning`）：以作物季次为单位，围绕棚区与作物批次组织六个模块，面向未来数日做计划。
- **方案与调整**（`guidance_rules`）：外来/专家方案必须注明「适用条件」；现场调整必须写明「观察依据」（现象与观察时间）再记动作。
- **事件重算**（`reschedule_events`）：病害、设备停机、配方更正、跨棚调苗、延迟采收、冷链能力变化六类事件发生后，受影响的后续任务随之级联重算；配方更正只追加新版本，已执行记录保留旧版本号。
- **离线记录**（`offline_record`）：田间记录区分 `occurred_at`（真实发生时间）与 `synced_at`（联网同步时间），补录数据按发生时间落位；同步迟到暴露的冲突标记为补录冲突并触发重算。
- **资源缺口**（`resources`）：生产经理提前看到未来数日的工人与滴灌台班缺口及冲突任务；农技人员对照方案与实际长势。
- **装箱溯源**（`traceability`）：以采收批次为锚点，装箱产品可沿批次查回棚区、作物批次、投入品批次、田间操作及操作人、当时执行的农技方案版本。

`sample` 中给出一条贯通样例：GH-027 番茄秋茬从土壤检测、基线方案适配、现场返盐调整、配方升级（TF-A v2→v3）、滴灌泵停机改期、离线巡查补录，到采收装箱与冷链窗口的完整链路。

## 本地校验

项目自带的测试会读取样例并检查领域标识、版本、记录类型、流程状态、事实说明、六类重算事件、离线发生时间、资源缺口与溯源链。后续服务应继续兼容这份公开资料约定。

```sh
python -m unittest discover -s tests -v
```
