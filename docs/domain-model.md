# 高原温室生产协同后台 · 领域模型

海拔约 1400 米的村庄新建近百座日光温室，外省技术员的通用水肥方案必须逐棚适配土壤；工人与滴灌设备有限，排产经常撞期。后台以**季次**为计划单位，围绕**棚区**与**作物批次**组织全部生产记录，用事件驱动的方式在扰动发生时重算后续任务，并支持从装箱产品一路追溯回棚区与技术版本。

## 1. 组织轴

| 轴 | 说明 |
| --- | --- |
| 季次（Season） | 计划与核算的单位。一个季次有起止日期、目标作物与目标产量，其下所有记录都挂在季次内。 |
| 棚区（GreenhouseZone） | 空间轴。近百座温室按滴灌分区归并，土壤检测、植保、水肥执行都落到棚区。 |
| 作物批次（CropBatch） | 生长轴。同一季次内同期定植、同一品种的苗为一个批次，经历 待定植 → 生长中 → 需干预 → 待采收 → 已采收 → 已交付 的状态流转。 |

任何一张业务记录必须能定位到（季次， 棚区， 作物批次）三元组中的适用部分；跨棚调苗等操作会同时引用来源与目标两个三元组。

## 2. 记录类型与职责

| 记录类型 | 职责 | 关键字段 |
| --- | --- | --- |
| 温室棚区 | 空间与滴灌分区主数据 | 棚号、分区、面积、土壤类型 |
| 作物季次 | 计划单位 | 起止日期、目标作物、目标产量 |
| 作物批次 | 生长单元，承载状态机 | 品种、定植日、当前状态 |
| 土壤检测 | 逐棚适配的输入 | 采样点、指标值、检测日期 |
| 育苗批次 | 苗的来源与去向 | 品种、数量、所在棚、可出苗日 |
| 农技方案 | 技术员给出的方案基线 | 方案版本、**适用条件**、目标棚区/批次 |
| 水肥配方 | 可执行的配方，按版本演进 | 配方版本、成分与用量、依据（方案版本 / 土壤检测） |
| 植保记录 | 病虫害监测与处置 | 病虫类型、发生范围、处置措施 |
| 田间操作 | 一切现场执行记录 | 操作人、操作类型、**发生时间**、录入时间 |
| 班次计划 | 工人与设备的占用计划 | 班次、工种、人数、设备槽位 |
| 采收订单 | 需求侧驱动 | 交期、数量、规格、冷链要求 |
| 采收批次 | 一次采收的实物单元 | 采收时间、数量、来源棚区/批次 |
| 冷链能力 | 逐日的预冷与运输能力 | 日期、可用容量 |
| 溯源档案 | 装箱后的追溯入口 | 装箱批、采收批次、投入品、操作人、技术版本 |

## 3. 方案与现场调整：两条证据链

- **专家建议 / 农技方案**必须写明**适用条件**（土壤指标区间、品种、生育期、海拔与温光前提）。方案只在条件满足的棚区/批次上生效；条件不满足时系统不得静默套用，只能生成"待适配"任务。
- **现场调整**（工人或农技员偏离方案执行）必须写明**观察依据**（实测数据、长势照片描述、异常症状），并生成新的配方/方案版本，而不是覆盖旧版本。
- 配方、方案均按**版本**演进：每次更正产生 `version + 1`，旧版本保留供追溯。水肥配方须标注其推导依据（哪个方案版本 + 哪次土壤检测）。

## 4. 事件驱动的任务重算

季次计划落成一张任务有向图（育苗 → 定植 → 水肥 → 植保 → 采收 → 装箱 → 交付），任务间以前置依赖连接。以下任一事件发生时，沿依赖边找出**受影响的后续任务集合**并重算其排期与资源占用，已完成的任务不受影响：

| 事件 | 影响面 | 重算规则 |
| --- | --- | --- |
| 病害发生 | 发病棚区及相邻棚区的作物批次 | 插入植保处置任务；批次状态转 需干预；采收最早时间后移安全间隔期 |
| 设备停机 | 停机滴灌分区覆盖的全部棚区 | 停机窗口内的水肥任务顺延或改派其他分区槽位；窗口外任务不动 |
| 配方更正 | 引用旧配方版本的未执行任务 | 未执行任务切换到新版本；已执行的不改，仅记入追溯 |
| 跨棚调苗 | 来源与目标两个棚区/批次 | 目标棚定植任务提前/新增，来源棚对应任务缩减；两棚水肥配方分别按各自土壤检测重算 |
| 延迟采收 | 该采收批次及其采收订单 | 采收任务后移；占用冷链能力的日期随之移动；订单交期冲突时标记缺口 |
| 冷链能力变化 | 变化日期之后的装箱与交付任务 | 按新容量重排装箱计划；排不下的订单提前暴露为缺口 |

重算结果以**计划版本**形式保存：每次重算生成新的计划版本并记录触发事件，保证"为什么改计划"可审计。

## 5. 离线记录与时间

田间网络不稳定，记录可离线产生、联网后同步。每条记录携带两个时间：

- `occurred_at`：真实发生时间（离线设备上填写，同步时不可改写）；
- `recorded_at`：到达服务器的时间。

排序、状态流转判定、重算影响面分析一律以 `occurred_at` 为准；`recorded_at` 仅用于审计"何时知情"。迟到记录到达后，若其 `occurred_at` 早于当前计划版本的起算点，则按第 4 节规则重新触发一次重算，而不是把记录简单追加在末尾。

## 6. 资源缺口预测

以班次计划与任务图为输入，向未来 N 日（默认 7 日）投影两类资源：

- **人工**：逐日逐工种的需求工时 vs 班次可用工时；
- **滴灌设备**：逐日逐分区的设备槽位需求 vs 可用槽位（扣除已申报的停机窗口）。

任何一天需求超过供给即形成缺口，缺口带出具体日期、工种/分区与缺口量，供生产经理提前调班、调设备或与客户协商交期。第 4 节的每次重算都会刷新这份投影。

## 7. 追溯链

产品装箱时生成装箱批，溯源档案固化以下链接，查询时沿链回走：

```
装箱批 → 采收批次 → 作物批次 → 棚区
                      ├─ 投入品（水肥配方版本、植保用药记录）
                      ├─ 操作人（田间操作记录）
                      └─ 技术版本（所依据的农技方案版本与配方版本）
```

由于配方与方案都是版本化且不可改写的，追溯到的永远是采收当时实际采用的技术版本，而不是事后更正后的版本。

## 8. 与公开资料约定的兼容

`fixtures/domain.json` 从 v1 升级到 v2 采用纯追加方式：原有字段名与取值不变，记录类型与流程状态只增不改，新增 `domain_events` 列表承载第 4 节的六类事件。v1 消费者可安全忽略新字段；`contracts/domain.schema.json` 同步放行新字段但仍关闭 `additionalProperties`，防止未约定的字段混入。
